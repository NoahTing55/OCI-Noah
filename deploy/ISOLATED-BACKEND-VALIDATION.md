# OCI-N&T API candidate validation and SQLite rollback rehearsal

This concentrated integration adds two **isolated**, operator-run diagnostics.
They intentionally cannot upgrade production API or authorize a restart.

## 1. Candidate schema exercise (already-local pinned image)

```bash
cd /opt/oci-nt
python3 deploy/isolated-candidate-schema.py \
  --db /opt/oci-nt/data/oci-nt.db \
  --sha <40-character-main-commit-sha>
```

The candidate image must already exist locally. The tool takes a WAL-aware
SQLite online backup into a private temporary directory, then runs only
`init_database()` inside that pinned API image with Docker
`--network none`, a temporary bind mount, and **fake application credentials**.
It does not start Uvicorn, use production `.env`, mount the live database,
or share the host Docker socket. The temporary copy is automatically removed.

A passing test confirms only that the candidate's schema initialization
completed on that copy, its integrity check passed and the original DB file
was unchanged. It does not prove API runtime compatibility, correctness of
OCI SDK side-effects, old-image rollback, or cross-process task quiescence.

## 2. Disposable restore of a verified release snapshot

Use the SHA256 from the manifest generated by
`deploy/verified-release-backup.py`.

```bash
python3 deploy/disposable-restore-drill.py \
  --snapshot /root/oci-nt-backups/release-snapshots/<verified-snapshot>.db \
  --sha256 <SHA256-from-its-manifest>
```

This checks SHA256, makes a fresh SQLite restore into a disposable directory,
verifies schema and integrity, and checks that the source snapshot stayed
unchanged. This is not a production restore rehearsal of the old API image.

## Remaining release blockers

- The currently running API is still on an older image without these
  maintenance/lease mechanisms.
- Complete tracing and draining of every OCI SDK call in all processes and
  detached threads remains unproven.
- Old API-image + database rollback compatibility and production startup
  migrations need end-to-end staging verification.
- A strictly approved, single-service API and worker update script with
  independent image pinning is not yet delivered.

Do **not** run `docker compose up -d`, activate maintenance, or change
production `.env` based on either diagnostic's success. Both intentionally
set `release_authorized: false`.
